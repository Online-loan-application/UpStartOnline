# UpStartOnline

UpStart Jamaica's loan application website.

## Run locally

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env.local` and set the Supabase project URL and anon key.
3. Run `npm run dev`.

## Supabase setup

Run [`supabase/schema.sql`](supabase/schema.sql) in the Supabase SQL Editor to create the `loan_applications` table and its row-level security policies. Add the local and deployed application URLs to the Supabase Auth redirect URL allowlist. The browser client uses only the public anon key; never put a service-role key in the frontend.

To enable the admin dashboard, run [`supabase/admin.sql`](supabase/admin.sql) after `schema.sql`, then run [`supabase/approval.sql`](supabase/approval.sql), [`supabase/approved_balance.sql`](supabase/approved_balance.sql), and [`supabase/admin_delete_loan_application.sql`](supabase/admin_delete_loan_application.sql). The deletion migration enables admins to remove an application and its application-linked records; it does not delete the applicant's Supabase Auth account or account activity. The approved-balance migration ensures that an approved application has an approved amount exactly equal to its requested loan amount, including existing approved applications; non-approved applications have no approved amount. The customer dashboard shows J$0 until approval, then displays the full requested amount as the balance. To grant admin access to an existing account, replace `ADMIN_EMAIL_HERE` in [`supabase/grant_admin_by_email.sql`](supabase/grant_admin_by_email.sql) with the account email, then run that script in the Supabase SQL Editor as a trusted project administrator. Admin access is stored in server-managed `app_metadata`, never user-editable metadata or browser code. Have the user sign out and back in so their access token refreshes. The dashboard is at `application.html?view=admin`; select an applicant to open their full application at `application.html?view=admin-applicant&id=...`. Both views require the admin role and database row-level security enforces access.

The customer dashboard links to dedicated Transfer (`application.html?view=transfer`) and History (`application.html?view=history`) pages. Run [`supabase/transfer_demo_serials.sql`](supabase/transfer_demo_serials.sql) after the migrations above to enable the serial demo, then run [`supabase/account_activity_transfers.sql`](supabase/account_activity_transfers.sql) to enable saved recipients, account activity notifications, and demo transfer processing. Run [`supabase/fix_demo_transfer_preview_recipient_column.sql`](supabase/fix_demo_transfer_preview_recipient_column.sql) after it to repair older installations whose preview table still requires recipient details. Run [`supabase/first_payment_authorization_demo_serial.sql`](supabase/first_payment_authorization_demo_serial.sql), [`supabase/second_demo_verification_serial.sql`](supabase/second_demo_verification_serial.sql), and [`supabase/third_transaction_reference_code_serial.sql`](supabase/third_transaction_reference_code_serial.sql) after the serial migration to set the first three serial display names and descriptions. The second step explicitly states that no fee or payment is required. Saved recipient information is stored under the signed-in user's row-level security policy and can be reused for later previews. Admins generate all four codes with one action and use one amount input plus a step selector to configure each stage separately. Codes are saved for authorized-admin retrieval until reset; the reset action clears all codes and sets each stage amount to J$0. The code value is available only through an admin-checked RPC and is not included in the user's serial metadata. Existing hash-only codes cannot be recovered; regenerate those once after applying the updated serial migration. The user cannot continue from the transfer preview until the first code exists and its amount is saved. Matching the first code moves the requested amount from available demo balance to the processing-demo total, which is listed per transfer on the dashboard; matching codes starts persistent 30-minute waits before each next stage appears. Activity history includes account creation, sign-in/sign-out, application submission/status changes, saved recipients, previews, and matched demo stages. These features are simulations only: no payment is submitted, no fee is charged, and no real funds move.

Build the production site with `npm run build`.
